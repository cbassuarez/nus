# nus 0.0.2 preview 3

## Release summary

- **Windows browsing starts with Chromium's sandbox.** The package now uses CEF's bootstrap and a signed nus DLL, preserving child-process sandbox policies.
- **Pages appear when shared GPU textures are unavailable.** Windows and Linux upload Chromium's page pixels directly; macOS keeps its accelerated path and can also display software frames.
- **Browser failures show an actionable page.** Startup failures, navigation timeouts and renderer crashes use nus's native transcript screens, so the error remains visible when Chromium cannot draw. Retry, Wait, Stop and Close remain available where appropriate.
- **Linux explains sandbox setup failures.** A preflight checks for usable user namespaces or an installed sandbox helper instead of entering a known failing Chromium startup path.
- **Releases test browsing.** Packaged applications must load HTTP, execute JavaScript, display verified pixels, and recover from timeout, crash and hang screens before publication.

## Validation and boundaries

Local macOS checks exercised both shared GPU textures and the BGRA upload path
with actual page pixels and
keyboard recovery from a silent HTTP response, a crashed renderer, and a
JavaScript infinite loop. The full native suite passed (574 tests, one
ignored), along with 25 release packaging tests and three support-policy tests. The publication workflow owns Windows/Linux runtime
validation and signing; local Mac evidence alone does not establish either.

Windows and Linux currently copy BGRA frames instead of importing shared GPU
textures, which can cost more CPU/bandwidth on large or rapidly changing pages.
Chromium GPU compositing and process sandboxing remain enabled. Linux needs
working user namespaces under its system/AppArmor policy or a properly
installed sandbox helper. The archive does not install a privileged helper.

The native watchdog works while the nus event loop is responsive; a hard
freeze of the entire application still requires restarting the process.
